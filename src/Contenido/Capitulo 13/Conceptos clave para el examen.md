**Identificar las diferencias entre los hilos de plataforma y los hilos virtuales.** Los hilos de plataforma **se corresponden** con los hilos del sistema operativo subyacente. Los hilos virtuales **son** más ligeros y **usan** un hilo portador solo cuando necesitan ejecutarse. Un hilo portador también **se ejecuta** sobre un hilo del sistema operativo. Los hilos virtuales **pueden ejecutarse** en `Executors.newVirtualThreadPerTaskExecutor()`. Al ser tan ligeros, no **necesitan** formar parte de un grupo de hilos (_thread pool_).

**Escribir código seguro para hilos (_thread-safe_).** La seguridad de hilos consiste en **proteger** los datos compartidos frente al acceso concurrente. Un monitor **puede usarse** para **asegurar** que solo un hilo **procese** una sección de código concreta cada vez. En Java, los monitores **pueden implementarse** con un bloque o un método `synchronized` o con una instancia de `Lock`. `ReentrantLock` **tiene** varias ventajas respecto a un bloque `synchronized`, como la posibilidad de **comprobar** si un bloqueo (_lock_) está disponible sin **bloquearse**, además de **admitir** la adquisición justa de bloqueos. Para **conseguir** la sincronización, dos o más hilos **deben coordinarse** en el mismo objeto compartido.

**Aplicar las clases atómicas.** Una operación atómica **es** la que **ocurre** sin interferencias de otro hilo. La API de concurrencia **incluye** un conjunto de clases atómicas similares a las clases primitivas, salvo que **aseguran** que las operaciones sobre ellas **se realicen** de forma atómica. **Hay que conocer** la diferencia entre una variable atómica y una marcada con el modificador `volatile`.

**Crear tareas concurrentes con un executor de hilos usando `Runnable` y `Callable`.** Un `ExecutorService` **crea** y **gestiona** un hilo o un grupo de hilos. Las instancias de `Runnable` y `Callable` **pueden enviarse** a un executor de hilos y **se completarán** con los hilos disponibles del servicio. `Callable` **difiere** de `Runnable` en que `Callable` **devuelve** un tipo genérico y **puede** lanzar una excepción verificada. Un `ScheduledExecutorService` **puede usarse** para **programar** tareas a una frecuencia fija o con un intervalo fijo entre ejecuciones.

**Usar las clases de colecciones concurrentes.** La API de concurrencia **incluye** numerosas clases de colecciones con soporte integrado para procesamiento multihilo, como `ConcurrentHashMap`. **Incluye** también la clase `CopyOnWriteArrayList`, que **crea** una copia de su estructura de lista subyacente cada vez que **se modifica** y **es** útil en entornos altamente concurrentes.

**Identificar problemas de hilos potenciales.** El interbloqueo (_deadlock_), la inanición (_starvation_) y el bloqueo vivo (_livelock_) **son** tres problemas de hilos que **pueden** ocurrir y **hacer** que los hilos **nunca** completen su tarea. El interbloqueo **ocurre** cuando dos o más hilos **quedan** bloqueados para siempre. La inanición **ocurre** cuando un hilo **tiene** denegado permanentemente el acceso a un recurso compartido. El bloqueo vivo **es** una forma de inanición en la que dos o más hilos **están** activos pero conceptualmente bloqueados para siempre. Por último, las condiciones de carrera (_race condition_) **ocurren** cuando dos hilos **se ejecutan** al mismo tiempo y el resultado **es** inesperado.

**Comprender el impacto de usar streams paralelos.** La API `Stream` **permite crear** streams paralelos con facilidad. Usar un stream paralelo **puede provocar** resultados inesperados, ya que el orden de las operaciones deja de ser predecible. Algunas operaciones, como `reduce()` y `collect()`, **requieren** un trato especial para **alcanzar** un rendimiento óptimo cuando **se aplican** a un stream paralelo.
